4. 用专用角色授权和撤权：展示下一请求权限变化；不要拿日常管理员角色做随意覆盖演示。

6. 查询日志并说明业务事务与成功日志一致性；用已有测试展示日志失败回滚，勿在现场业务库破坏日志表。

## 3 需要自己讲清楚的问题

| 问题 | 应结合代码解释的要点 |
| --- | --- |
| 怎么证明不是 Boot？ | 无 Boot 父 POM、starter、插件和启动类；Servlet 初始化器创建两个 Spring 容器，WAR 由 Tomcat 加载 |
| 为什么分父子容器？ | Service/数据访问在根容器；Controller/Advice/权限切面在 MVC 容器，避免重复扫描及代理失效 |
| 为什么登录后重取 CSRF？ | Session ID 与令牌轮换，登录前令牌不能继续做写操作；CSRF 与登录鉴权各自解决不同问题 |
| 为什么管理员也检查权限？ | 角色是权限集合，ADMIN 不绕过检查；撤权后下一请求按实时有效关联判断 |
| 注解为什么可能不生效？ | 必须经 Spring 代理访问；内部 `this` 调用绕过代理，public 非 final 的外部入口要自己声明权限 |
| 日志为什么不全用新事务？ | 成功日志应与业务一起提交/回滚；失败日志才独立记录，否则可能留下业务已失败但日志成功的矛盾状态 |
| 最后一个管理员怎么保护？ | 授权修改与账号启停共用锁顺序，事务内再查权限及剩余有效管理能力，不能只看 ADMIN 名称 |
| 版本号有什么用？ | 状态修改按客户端版本更新，过期版本返回 409；测试覆盖并发只有一个成功 |
| 为什么不直接 JOIN 后分页？ | 一人多角色会产生多行，分页对象和总数被改变；先分页用户，再批量组装 |
| N+1 优化提升了多少？ | 只测 SQL 次数，没有可靠端到端耗时；低效方法只是测试对照，不是历史线上故障 |
| H2 通过够不够？ | 不够；MySQL 外键、锁、事务和真实容器行为需单独验收；各专项记录分别给出范围 |
| AI 做了什么？ | 按实际交互回答，包含实现、调试、测试和文档；未完成人工复核不能回答为已独立完成 |

## 4 真实问题案例：测量工具漏计 SQL

复现条件：B17 角色分页测试单独执行时通过，但放入多 Spring 上下文的全量测试时，StatementHandler 计数探针漏计分页 COUNT。问题发生在测量工具，不能据此声称产品少发了一条 SQL。

定位：比较独立测试与全套运行的 SQL 计数窗口，确认探针没有稳定覆盖实际 JDBC 查询。修改：在测试 DataSource 中包装连接的 `prepareStatement`，将总数、分页和角色查询统一计数；保持期望值 3，不降低断言绕过问题。

回归：重新执行全套测试，并在新 MySQL 空库中运行 10/20/100 条页各 5 轮，断言完整分页响应一致；最终实现和证据在 `447904c`，详见[B17 验证记录](../verification/B17用户角色查询优化验证记录.md)。这是实际处理过的问题；其定位与修改有 AI 参与，学生独立复现和理解情况待记录。
