# B-13 角色分配与权限配置

日期：2026-10-08。沿用 V1.0 的权限编码与“目标集合覆盖当前集合”规则，不修改数据库结构。

## 接口与请求

| HTTP 接口 | 所需有效权限 | 请求体 |
| --- | --- | --- |
| `PUT /api/users/{id}/roles` | `cms:role:assign` | `{"roleIds":[2,3]}` |
| `PUT /api/roles/{id}/permissions` | `cms:permission:manage` | `{"permissionIds":[5,6]}` |

上述 ID 仅为格式示例，必须使用当前数据库实际 ID。成功返回 HTTP 200 和统一响应：code 为 OK、data 为 null，并包含 requestId。随后可用 B-12 的角色有效权限接口或目标账号的 `/api/auth/me` 检查生效结果。

所有写请求要求登录 Cookie、`Content-Type: application/json` 和同一会话的 `X-CSRF-Token`。通过 `/api/auth/csrf-token` 取得 Token；登录成功后会轮换会话和 Token，因此必须再获取一次。

请求集合完整替换目标原有配置。重复 ID 自动去重；`[]` 清空目标关系。未提供字段、null 集合、null 元素、非正 ID，以及原始集合超过 500 项均拒绝。省略字段与空数组语义不同。重复提交同一集合不会产生重复关系，但不承诺保留内部关系行 ID 或最初授权时间。

目标用户必须 ACTIVE，目标角色及集合内的角色/权限必须 ENABLED，均不得逻辑删除。服务端忽略请求中的 createdBy、userId 等额外字段；路径决定目标对象，真实操作者来自会话。新关系 created_by 由服务端写入真实操作者 ID。

## 错误与安全规则

| 场景 | HTTP / 业务码 |
| --- | --- |
| 未登录、无效账号或会话 | 401 / AUTH_UNAUTHENTICATED |
| 缺少操作权限、CSRF 缺失或不匹配 | 403 / AUTH_FORBIDDEN |
| 路径 ID 或集合格式不合法 | 400 / COMMON_VALIDATION_ERROR |
| 集合中任意角色/权限不存在、停用或删除 | 400 / COMMON_VALIDATION_ERROR，整体不修改 |
| 路径目标不存在或已删除 | 404 / COMMON_NOT_FOUND |
| 路径目标已停用 | 409 / COMMON_CONFLICT |
| 操作将导致系统失去最后一个 RBAC 管理账号 | 409 / COMMON_CONFLICT，整体回滚 |
| 写入中途出现未知异常 | 500 / COMMON_INTERNAL_ERROR，整体回滚 |

管理能力由实际有效权限决定，不按 ADMIN 角色名称硬编码。最后一个 RBAC 管理账号指：ACTIVE 且未删除，并通过有效角色同时拥有 `cms:role:assign` 与 `cms:permission:manage` 的账号，两种权限可以来自不同角色。

每次修改后必须至少保留一个这样的账号。因此可清空普通用户角色，也可在另有有效管理账号时移交或撤销原管理员权限；不能通过修改用户角色或角色权限把所有管理能力都撤掉。若初始化数据本身没有任何完整 RBAC 管理账号，需要先修复初始化或通过合法授权建立管理账号；本接口不提供绕过鉴权的自救入口。

当前 Controller 采用显式权限保护；事务内在获取写锁后重新读取操作者状态和有效权限，避免请求等待期间权限已撤销却继续执行。B-14 再接入统一注解和权限 AOP。授权变更在下一请求生效，当前请求中的身份快照不原地修改。

## 事务和并发实现

`RbacAssignmentService` 使用 Spring 事务和 READ_COMMITTED 隔离级别。两类操作先锁定现有 `cms:role:assign` 权限行作为共同的管理写锁，然后校验真实操作者、锁定目标和待分配对象、删除旧关系、批量写入新关系、检查剩余管理账号。异常时删除和新增均回滚。

锁定查询配置 `flushCache=true`、`useCache=false`，避免 MyBatis 在事务内复用等待写锁前的旧权限结果。写入采用参数绑定；数据库组合唯一约束继续兜底，不通过拼接客户端文本构造 SQL。

同一目标并发提交按锁顺序串行执行，最终保留最后成功提交的完整集合，不会拼接两份请求。当前未引入 expectedVersion；前端编辑冲突检测不在本批范围。

共同写锁适合课程 MVP 的低频管理操作。其保护范围是这两个 B-13 写入口；直接 SQL、外部程序及后续账号启停入口不能自动受保护。B-11 实现最后管理员的账号启停约束时，需要遵循同一锁顺序和完整性规则。真实 MySQL 的锁行为仍待验收。

## ApiFox 手工验收准备

提供 [Postman v2.1 格式集合](B13角色权限配置.postman_collection.json)，用于导入 ApiFox/Postman。已检查 JSON 和脚本结构，尚未在 ApiFox 客户端执行，不是已验收的 ApiFox 导出。

1. 使用隔离测试数据库，准备管理账号、普通账号和非管理员测试角色。
2. 填写 baseUrl、username、password；开启 Cookie 保持。集合中没有真实密码。
3. 按 01–06 获取 Token、登录、刷新 Token并读取角色/权限。若导入后脚本未保存 Token，将响应 data.token 手工填入 csrfToken。
4. 填写 targetUserId、targetRoleId、roleIds、permissionIds。两个集合变量必须是 JSON 数组文本，不能是逗号分隔字符串。
5. 执行 07–09 覆盖和读取；以目标账号另开会话调用 me 验证角色变化。
6. 执行 10、11 验证缺少 CSRF 和非法 ID，预期分别 403、400；12 退出。
7. 另用普通账号、停用对象及最后管理员场景复核越权与冲突。不要在共享演示数据上直接套用示例 ID。

密码仅填写在自己的本地环境，不提交含凭证的导出文件。自动回滚与并发验证见 [B-13 验证记录](../verification/B13角色权限配置验证记录.md)。本批未执行真实 MySQL 数据修改，也没有新增部署 SQL；B-08 的默认 USER 角色准备要求仍然有效。
