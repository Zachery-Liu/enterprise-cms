# B-11 用户分页与账号启停

日期：2026-10-11。分支 `feat/user-administration`，基于 B-16 `a65db1a`。传统 SSM、JDK 17、MySQL 8.0、外部 Tomcat；无新增数据库迁移。

## 1 用户列表

`GET /api/users`，需要 `cms:user:read`。使用现有 Session，响应设置 `Cache-Control: no-store`。

| 参数 | 规则 |
| --- | --- |
| page | 默认 1，正整数，分页偏移量不能溢出 |
| size | 默认 20，范围 1～100 |
| username | 1～64 字符，不能全为空白；用户名包含匹配 |
| status | ACTIVE 或 DISABLED |
| from / to | 创建时间范围，可单边提供；包含边界 |

时间须为带偏移量的 ISO 8601，转换为 UTC 后年份为 1000～9999，精度最多毫秒；from 不得晚于 to。URL 中 `+08:00` 的加号应编码为 `%2B`，也可直接使用 Z。省略可选参数表示不限；未知/重复参数和非法值返回 400。

用户名使用绑定参数，关键词中的 `%`、`_`、`!` 按普通字符查询，不允许它们扩大匹配范围。大小写规则沿用 MySQL 的 utf8mb4_unicode_ci。条件按 AND 组合，逻辑删除用户不出现在列表，停用用户仍可查询。

固定按 `created_at DESC, id DESC` 排序。使用 MyBatis-Plus 数据库分页，单次请求的总数和本页采用只读 REPEATABLE_READ 事务。不同请求之间新增账号仍可能导致页码移动，未提供跨请求快照。

响应为公共 `ApiResponse<PageResponse<UserListView>>`，data 包含 records、total、page、size。每个账号保留以下基础字段，并附带下文说明的 roles：

```json
{
  "id": 20,
  "username": "demo",
  "displayName": "Demo",
  "status": "ACTIVE",
  "version": 0,
  "createdAt": "2026-10-11T01:00:00.123Z",
  "updatedAt": "2026-10-11T01:00:00.123Z"
}
```

不返回密码摘要、密码变更时间、内部 Session 或角色编辑字段。2026-10-12 B-17 为列表每行新增只读 roles 数组，角色包含 id、code、name、description、status；无角色返回 []。管理展示包含停用角色，过滤逻辑删除角色，停用账号也保留分配情况。该数组不能作为有效权限判断依据，身份鉴权仍使用原有效角色查询。详见[B-17 优化说明](../optimization/B用户角色查询优化.md)。无匹配返回空 records 和 total=0；超出最后一页仍保留正确 total。

## 2 账号启停

`PUT /api/users/{id}/status`，需要 `cms:user:manage`、Session Cookie 与登录后最新 `X-CSRF-Token`。

```json
{
  "status": "DISABLED",
  "version": 0
}
```

- id 必须为正整数；status 只能是 ACTIVE 或 DISABLED。
- version 必填，为非负整数，来自最新用户列表或上次成功写入响应。旧版本返回 409，刷新后再操作。
- 状态实际变化时版本加 1，服务端自动填写 updatedBy 和 UTC updatedAt；响应 data 为更新后的 UserAdminView。
- 相同状态且版本仍匹配时返回成功，不增加版本。重复提交旧版本仍返回 409。
- 额外的 username/passwordHash/roleIds/updatedBy/deleted 等字段不用于更新；角色配置继续走 B-13。
- 不存在或逻辑删除账号返回 404，停用账号可重新启用。
- 一律拒绝停用自己的账号，返回 409。
- 停用任何账号后必须仍保留一个同时具有 cms:role:assign 和 cms:permission:manage 的有效账号；否则回滚并返回 409。不依赖 ADMIN 角色名称判定。

管理事务先获取与 B-13 共用的管理锁，再检查操作者当前有效状态和权限，随后锁定目标。排队期间即使已有请求权限快照，真正写入前也重新校验，防止使用已经撤销的权限。状态变更使用 MyBatis-Plus 乐观锁，并校验影响行数。

## 3 日志和历史数据

启停请求记录 `USER / SET_STATUS`，目标类型 USER，目标 ID 为账号 ID。成功日志与账号状态同事务；日志保存失败会回滚状态、版本和更新人；失败结果按 B-15 独立记录。相同状态的成功请求也会记录一条成功操作日志。

本接口仅更新账号状态、版本和更新审计字段，不删除账号、角色关系、历史文章、审核历史或既有日志。停用后不能登录，已有会话在下一次受保护请求检查到停用状态时返回 401 并失效；恢复账号后可以重新登录。

已验证 B 侧角色关系和历史日志保留。真实 A 文章/审核表的联合验收仍需 A 接入，不能以 B 测试代替。

## 4 ApiFox 用例

导入 [B11用户管理.postman_collection.json](B11用户管理.postman_collection.json)，共 19 个请求。该集合是交付用例，尚未声称已完成 ApiFox 人工点测。

1. 在隔离环境运行；设置 baseUrl（如 http://localhost:8080/enterprise-cms）、adminUsername、adminPassword。管理员需具备上述查询与启停权限。
2. 清除该服务器旧 Cookie，启用 Cookie 自动保存。
3. 按序执行。集合自动生成并注册一个普通临时账号，再由管理员查询、停用、测试版本冲突和恢复。
4. 集合最后验证恢复后的账号能登录，普通账号不能查询用户。默认 USER 角色不应预先获得 cms:user:read。
5. 临时账号及操作日志会保留，不自动删除。失败时先查看错误，不盲目重试写请求；可重新从头运行创建新的临时账号。
6. 请勿把填入真实密码的集合导出并提交 Git。请求集合脚本为 Postman 兼容语法，导入后需检查断言是否保留。

自动化测试另覆盖禁止自停用、最后管理员保护、停用登录拒绝、旧会话失效、并发启停与授权、锁等待后撤权、故障回滚。结果见[B-11 验证记录](../verification/B11用户管理验证记录.md)。
