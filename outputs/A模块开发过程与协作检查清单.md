# CMS 双人协作规划复核与 A 模块开发检查清单

修订日期：2026-10-08。本轮 A 旧实现不作为基础，B 保留 `origin/feature/security@dff0cca` 的已实现业务并迁移无 Boot 的公共工程。执行任务以[A 逐项清单](../docs/tasks/A模块逐项任务清单.md)和[B 逐项清单](../docs/tasks/B模块逐项任务清单.md)为准；原检查项不代表已完成。B 权限 AOP 和操作日志尚待交付。

## 1 复核结论

现有规划适合作为企业级 CMS 的长期蓝图，但不适合作为两人课程项目的首期开发清单。课程评分重点是 SSM 整合、用户权限、文章、分类、审核状态、日志、MyBatis Plus、SQL 优化、RESTful 接口和可运行交付。若直接实现动态内容模型、多站点、数字资产、复杂审批和多渠道发布，两人很容易在基础必做项尚未稳定时耗尽时间。

建议采用两层范围：

- 企业级需求文档作为产品愿景和结题报告的需求分析来源。
- 课程 MVP 作为实际开发基线，只实现能形成“登录 -> 编辑文章 -> 提交审核 -> 审核 -> 发布或下架 -> 查询日志”的闭环。

A 的首要目标应从“内容模型与资产平台”收缩为“分类与文章领域的完整闭环”。数字资产、动态字段、多站点和复杂版本对比均放到基础功能稳定之后。

## 2 原分工需要调整的地方

### 2.1 范围过大

动态内容模型、数字资产安全扫描、跨站点引用、多渠道发布和复杂版本冻结均属于企业级扩展。它们不是评分表中的明确必做项，不宜在课程 MVP 前期投入。

### 2.2 状态所有权不清晰

原方案中 A 管内容版本，B 管审核和发布状态，但文章状态最终仍保存在文章领域。如果 A、B 都直接修改文章状态，很容易产生重复逻辑和非法状态。

修订原则：文章状态机及其数据库更新只由 A 维护；B 提供登录用户、角色、权限判断和操作日志基础能力。B 开发的审核页面通过 A 的文章状态接口操作，不直接更新文章表。

### 2.3 计分点覆盖不完整

课程明确要求注册、登录、退出、角色分配、Spring AOP 接口权限校验、操作日志、统一异常、参数校验、MyBatis Plus 高级特性和 N+1 优化。原企业级分工提到了能力，但没有落实到明确负责人和可验收产物。

## 3 修订后的双人分工

| 负责人 | 代码所有权 | 主要功能 | 必须交付 |
| --- | --- | --- | --- |
| A 内容领域 | `cms_category`、`cms_article`、`cms_article_status_history`；分类与文章的 Controller、Service、Mapper、DTO、VO | 多级分类、文章 CRUD、分页与多条件搜索、逻辑删除、提交审核、审核状态机、批量发布、下架 | 页面或接口、单元测试或集成测试、ApiFox 用例、SQL 与设计说明 |
| B 身份与基础设施 | `sys_user`、`sys_role`、`sys_permission`、用户角色和角色权限关系表、`sys_operation_log`；认证、授权和日志切面 | 注册、登录、退出、角色分配、细粒度权限、Spring AOP 权限校验、操作日志、统一异常、公共参数校验 | 页面或接口、权限注解、日志切面、异常处理、ApiFox 用例 |
| B 主维护，双方验收 | 传统 SSM 项目骨架、公共配置与部署；双方负责总图、联调和演示 | 无 Boot 的 Maven WAR、显式容器、数据源、事务、MVC、会话与测试迁移 | 可启动基线、配置和外部 Tomcat 部署说明；A 接入验收记录 |

为了避免后端代码冲突，文章状态转换逻辑只放在 A 的 `ArticleLifecycleService` 中。B 可以负责审核页面，但必须调用 A 提供的审核接口。

## 4 A 与 B 的接口契约

### 4.1 B 先提供给 A 的公共能力

- 当前用户上下文：至少包含 `userId`、用户名、角色或权限集合。
- 权限注解，例如 `@RequirePermission("cms:article:create")`。
- 权限编码沿用公共契约：`cms:article:read`、`cms:article:create`、`cms:article:edit`、`cms:article:delete`、`cms:article:submit`、`cms:article:audit`、`cms:article:publish`、`cms:article:offline`，以及分类权限。
- 操作日志注解或统一记录方式，例如 `@OperationLog(module = "文章管理", action = "发布")`。
- 统一返回结构、业务异常类型、错误码和分页返回结构。

如果 B 的切面尚未完成，A 可以先开发 Service 规则和持久层。后台接口最终验收必须接入真实权限；临时保护须与 B 约定并随后替换，不使用权限空实现，不在各 Controller 复制权限逻辑。

### 4.2 A 提供给 B 的文章状态接口

建议至少包含以下接口，最终路径以双方约定为准：

| 方法与路径 | 权限 | 作用 |
| --- | --- | --- |
| `POST /api/articles` | `cms:article:create` | 新增草稿 |
| `PUT /api/articles/{id}` | `cms:article:edit` | 编辑允许修改的文章 |
| `GET /api/articles` | `cms:article:read` | 分页、多条件、排序查询 |
| `DELETE /api/articles/{id}` | `cms:article:delete` | 逻辑删除 |
| `POST /api/articles/{id}/submit` | `cms:article:submit` | 提交审核 |
| `POST /api/articles/{id}/approve` | `cms:article:audit` | 审核通过 |
| `POST /api/articles/{id}/reject` | `cms:article:audit` | 审核退回并记录原因 |
| `POST /api/articles/{id}/publish` | `cms:article:publish` | 发布已审核文章 |
| `POST /api/articles/{id}/offline` | `cms:article:offline` | 下架已发布文章 |
| `POST /api/articles/batch-publish` | `cms:article:publish` | 批量发布符合条件的文章 |

接口必须由服务端校验权限和当前状态，不能只依赖页面隐藏按钮。

## 5 A 的文章状态机

建议课程 MVP 使用以下状态：

```text
DRAFT -> PENDING -> APPROVED -> PUBLISHED -> OFFLINE
  ^         |           |
  |         v           v
  +------ REJECTED    REJECTED
```

实际规则建议简化为：

- 新建文章为 `DRAFT`。
- `DRAFT` 或 `REJECTED` 可编辑并提交为 `PENDING`。
- `PENDING` 只能由具备审核权限的用户执行 `APPROVED` 或 `REJECTED`。
- `APPROVED` 才能发布为 `PUBLISHED`。
- `PUBLISHED` 可以下架为 `OFFLINE`。
- 已发布文章再次编辑时，课程 MVP 可要求先下架；若时间充足，再实现“线上版本与新草稿并存”。
- 删除统一采用逻辑删除。已发布文章必须先下架，再允许删除。
- 状态更新 SQL 应同时校验原状态，例如 `WHERE id = ? AND status = 'PENDING'`，避免重复审核和并发覆盖。

不要让 Controller 直接修改状态字段，也不要提供可由客户端任意传入状态的通用更新接口。

## 6 A 的开发过程与检查门禁

### A-SSM 基线接入门禁

- [ ] B-M01～B-M05 迁移验收通过，B-M06 提供接入说明。
- [ ] A 从验收提交建立新分支，不混入旧实现或本地替代认证。
- [ ] 本机外部 Tomcat WAR 可使用真实登录、当前用户、CSRF、统一响应与 requestId。
- [ ] content 组件、Mapper/XML、分页、乐观锁及审计填充接入 B 公共配置。
- [ ] 内容建表脚本的自指 CHECK 已知阻塞已修复或替换，并通过目标 MySQL 空库验证。

### A0 范围和契约冻结

产物：A 的功能清单、状态图、接口表、权限编码、字段表。

通过条件：

- 明确哪些功能属于 MVP，哪些属于加分项。
- A、B 对统一返回结构、登录上下文、权限注解和日志方式达成一致。
- 数据表维护人明确，双方不直接修改对方负责的表结构。

### A1 数据库与设计图

产物：分类表、文章表、必要索引、E-R 图和文章流程图。

建议字段：

- `cms_category`：`id`、`parent_id`、`name`、`sort_order`、`status`、`deleted`、创建与更新时间。
- `cms_article`：`id`、`title`、`summary`、`content`、`category_id`、`author_id`、`status`、`review_comment`、`publish_time`、`version`、`deleted`、创建与更新时间。

通过条件：

- 主键、非空、长度、默认值和必要索引明确。
- `category_id`、`author_id` 的关联关系在 E-R 图中可见。
- 标题、分类、状态、作者、发布时间等常用筛选字段具备合理索引。
- 使用 `version` 做乐观锁，使用 `deleted` 做逻辑删除，使用自动填充维护审计时间。
- SQL 脚本可以从空数据库一次执行成功。

### A2 多级分类管理

产物：新增、编辑、树形查询、排序、启停和删除接口。

通过条件：

- 禁止将节点移动到自身或后代节点下。
- 删除前检查子分类和关联文章；有引用时拒绝删除或给出明确处理方式。
- 停用分类后不能创建新文章，但历史文章仍可查询。
- 树形查询没有逐节点访问数据库造成的 N+1 问题。
- 名称、排序值和状态经过参数校验。

### A3 文章基础管理

产物：新增、编辑、详情、逻辑删除、恢复、分页查询和多条件模糊搜索。

通过条件：

- 查询支持标题、分类、状态、作者、时间范围和排序。
- 所有查询默认过滤逻辑删除数据。
- 编辑时使用版本号检测并发冲突，不静默覆盖。
- 富文本至少进行服务端危险内容处理或采用明确的安全输出策略。
- DTO、Entity、VO 分离，Controller 不直接接收和返回数据库实体。
- 分页查询不在循环中逐条查询分类或作者。

### A4 审核与发布状态流转

产物：提交、通过、退回、发布、批量发布和下架接口。

通过条件：

- 每个操作只允许合法的源状态。
- 审核人不能通过直接修改文章接口绕过状态机。
- 退回必须记录原因。
- 批量发布逐项校验状态和权限，并明确采用“全部成功才提交”还是“逐项返回结果”；课程演示更推荐逐项返回结果。
- 重复提交、重复审核、重复发布不会产生错误状态。
- 所有关键操作都能被 B 的日志机制记录。

### A5 MyBatis Plus 与 SQL 优化

产物：分页插件、条件构造器、逻辑删除、自动填充、乐观锁及一项可说明的 SQL 优化。

通过条件：

- 分页不是在内存中截取结果。
- 排序字段使用白名单，不能把客户端字符串直接拼入 SQL。
- 文章列表的分类名和作者名通过联表或批量查询获得，不产生 N+1。
- 对优化前后的 SQL 次数或执行计划保留截图或说明。
- 批量操作使用批量 SQL 或批处理，不在循环中逐条提交事务。

### A6 测试与联调

产物：ApiFox 集合、测试账号说明、关键用例结果和缺陷记录。

至少验证：

1. 正常创建分类和文章。
2. 非法分类层级被拒绝。
3. 分页、多条件和排序结果正确。
4. 两次使用旧版本号保存时，后一次发生冲突。
5. 草稿不能直接发布。
6. 无审核权限用户不能审核。
7. 退回后可编辑并重新提交。
8. 批量发布包含非法状态文章时，返回结果符合约定。
9. 已发布文章先下架后删除。
10. 所有关键操作均能查询到日志。

通过条件：主流程从登录到下架可完整演示；接口异常统一返回，不暴露堆栈；无阻断缺陷。

### A7 文档与过程材料

产物：模块说明、接口文档、SQL 脚本、设计图、测试记录、AI 交互记录和修改痕迹。

通过条件：

- 每个功能能对应到评分点和验收用例。
- Git 提交粒度可读，能体现从设计、实现、修复到优化的过程。
- AI 生成代码均经过人工检查，能够解释关键状态机、SQL 和权限调用。
- 结题报告记录至少一个真实问题、定位过程、修改方案和验证结果。

## 7 推荐开发顺序

```text
B 迁移传统 SSM，同时 A 重做领域、数据库和设计图
  -> A-M00 接入 B 验收基线
  -> A2 分类管理 / B-14 权限 AOP 联调
  -> A3 文章 CRUD 与查询（使用真实登录和批量作者读取）
  -> A4 审核发布、状态历史 / B-15 操作日志联调
  -> A5 MP 特性与 SQL 优化
  -> A6 联调和异常用例
  -> A7 文档与演示材料
  -> 有余力再做素材上传或版本历史
```

不要先开发素材库。只有当文章、分类、权限、审核、日志和完整演示均通过后，素材上传才作为扩展加入。

## 8 协作规则

- A、B 使用各自功能分支，小步提交；合并前执行启动测试和核心接口回归。
- 公共 DTO、错误码、权限编码和数据库公共字段的修改必须先同步。
- 每天至少联调一次主链路，避免最后集中解决接口差异。
- 不允许跨模块直接操作对方的数据表；跨模块只调用约定服务或接口。
- 数据库迁移脚本按编号管理，禁止双方反复编辑同一个初始化脚本而不沟通。
- 每个接口完成后立即保存 ApiFox 请求和响应示例。
- 保留需求变更、AI 对话、报错信息、修复前后代码差异和测试结果，满足过程痕迹评分。

## 9 A 模块完成定义

A 模块只有在以下条件全部满足时才算完成：

- 分类和文章核心接口可运行。
- 文章状态机不能被普通编辑接口绕过。
- 登录、权限和日志能力已与 B 联调。
- 分页、筛选、排序、逻辑删除、自动填充和乐观锁均可演示。
- 已证明文章列表不存在明显 N+1 查询。
- ApiFox 主流程和异常流程均有记录。
- SQL、接口、设计图和过程材料齐全。
- 从登录到文章下架可以在一套环境中完整演示。

## 10 暂缓项

以下功能保留在企业级需求文档中，但不进入第一轮实现：

- 动态内容类型和字段设计器。
- 完整数字资产库、恶意文件扫描和派生图片处理。
- 多站点、多语言和跨渠道发布。
- 可视化流程设计、会签和复杂条件审批。
- 在线版本与草稿版本并存、可视化版本差异。
- Elasticsearch、CDN、自建消息中心和大规模性能指标。

第一轮结束后，若时间充足，优先扩展“文章附件上传与引用”，其次再做“文章版本历史”。
